# Ciphera v0.1 « je déploie mon app » — plan d'implémentation

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** livrer un Ciphera mono-serveur installable par `curl | sh`, où un utilisateur se connecte avec une 2FA, branche un dépôt GitHub et obtient son app en ligne en HTTPS, avec logs, variables secrètes et rollback.

**Architecture :**
- **Workspace Cargo.** Il contient `control-plane` (Axum + SQLx, sert la SPA via rust-embed), `agent` (QUIC/mTLS, bollard, BuildKit), `proxy` (Pingora + instant-acme), `cli`, `proto`, `api-types`, `pki` et `shared`.
- **Interface.** La SPA React 19 vit dans `web/` et porte les écrans de `prototypes/dashboard/` sans les redessiner.
- **Livraison.** Le travail avance par tranches verticales : chaque tâche livre un écran porté, son endpoint, son action agent et ses tests.

**Tech Stack :**
- **Rust :** Rust stable, axum, sqlx (postgres, macros, migrate), rustls, rust-embed, utoipa, argon2, totp-rs, webauthn-rs, age, rcgen, quinn, postcard, bollard, rusqlite, pingora, instant-acme, clap, tracing + opentelemetry, testcontainers.
- **Web :** React 19, Vite, TypeScript, TanStack Router/Query, Tailwind v4, shadcn/ui, lucide-react, @fontsource/geist, openapi-typescript, Vitest + Testing Library, MSW, Playwright.

**Spec :** `docs/superpowers/specs/2026-11-21-ciphera-v0.1-design.md`. À lire avec :
- `docs/design/screens.md` (contrat écran → route → endpoint) ;

## Global Constraints

- **Licence et plateformes :**
  - Licence `AGPL-3.0-only` dans chaque `Cargo.toml` et dans `web/package.json`.
  - Serveur cible : Linux `x86_64-unknown-linux-musl` et `aarch64-unknown-linux-musl`, avec Debian, Ubuntu et Fedora testés en CI.
- **Exécution de commandes :**
  - Aucun shell construit à partir d'une entrée (CWE-78).
  - Sous-processus autorisés : seulement `docker compose`, `railpack` et `git`, avec un tableau d'arguments fixe et des entrées validées par regex en liste blanche.
- **Secrets :**
  - Chiffrés avec age côté serveur, en **écriture seule** : l'API ne renvoie jamais une valeur secrète.
  - Jamais dans les logs, jamais dans `localStorage`.
- **Isolement des apps déployées** (revue security-audit, étape 8) :
  - Une app déployée ne joint jamais `ciphera-postgres` ni `buildkitd`. Ces deux conteneurs vivent sur le réseau interne `ciphera-internal` ; chaque projet a son réseau `ciphera-p-<project_id>`.
  - Une app déployée ne reçoit jamais de privilèges hôte : pas de `privileged`, pas de réseau, PID ou IPC `host`, aucun `cap_add`, aucun `devices`, pas de montage du socket Docker ni de chemin hôte. Les conteneurs tournent avec `no-new-privileges`.
  - Les entitlements BuildKit `security.insecure` et `network.host` sont refusés.
- **Ressources tierces :** aucune ressource tierce chargée par le panneau, qu'il s'agisse de CDN, de polices ou de favicons. Le panneau fonctionne hors ligne.
- **Paramètres fixés par le spec :**

| Paramètre | Valeur |
|---|---|
| Hachage des mots de passe | argon2id |
| Mot de passe de la base | `OsRng` 32 octets, fichier en mode 600, jamais affiché |
| Jeton de setup | usage unique, invalide dès qu'un admin existe |
| Lien d'invitation | usage unique, valable 72 h |
| Inscription publique | désactivée par défaut |
| Images conservées par environnement pour le rollback | N = 5 |
| Collecte des métriques | toutes les 30 s ; rétention 30 jours, agrégats horaires au-delà de 24 h |
| Rôles | `owner`, `admin`, `ops`, `developer`, `viewer`, avec la matrice par défaut fixe de `prototypes/dashboard/Team.jsx` |
| Panneau avant domaine | HTTPS auto-signé sur le port **8443**, empreinte SHA-256 affichée par `install.sh` ; le port 80 ne fait qu'une redirection 301 vers HTTPS sans contenu *(choix du rédacteur pour le port)* |
| Releases | `SHA256SUMS` signé minisign ; `install.sh` s'arrête sans rien installer si une vérification échoue |
| Agent local | passe par QUIC + mTLS et `proto` v1, comme s'il était distant |

- **Écrans :** chaque écran de `prototypes/dashboard/` est **porté** : on garde la structure, les libellés FR et les tokens, en convertissant les `window.*` en imports. Il n'est jamais redessiné.
- **Mocks :** les données factices deviennent des fixtures MSW (`web/src/mocks/fixtures/`) ou des seeds de test, jamais des données de production.
- **Mémoire :** après chaque tâche, `python .agents/hooks/memory_hook.py note` ou une entrée dans `.agents/memory/journal.md`, et la ligne de `docs/design/screens.md` passée à `branché`.
- **Avant chaque commit :** `npx design-to-dev ai-traces scan . --strict` et `npx design-to-dev security-kit verify .`.
- **Interdit dans les fichiers :** aucun `Co-Authored-By`, aucun commentaire « Generated by ».

## Review Focus

1. **Webhook GitHub falsifié ou rejoué.** Si la signature est fausse ou absente, si la livraison est déjà vue (`X-GitHub-Delivery`) ou si le dépôt est inconnu, la réponse est 401/404 et aucun déploiement n'est mis en file. Test : Task 23.
2. **Le nouveau conteneur échoue à son healthcheck.** L'ancien continue de servir, aucune route n'est basculée, le déploiement passe `failed` et le nouveau conteneur est supprimé. Test : Task 25.
3. **Deux déploiements simultanés sur le même environnement** (push + bouton). Le second attend en file (`queued`), jamais en parallèle. L'annulation pendant le build nettoie conteneurs et build. Test : Task 25.
4. **L'agent se déconnecte en plein déploiement.** À la reconnexion, le plan de contrôle réconcilie l'état depuis l'agent. Pas de déploiement bloqué en `running` pour toujours : il passe `failed` après 10 min sans nouvelles. Test : Task 19 + Task 25.
5. **Jeton de setup rejoué ou deux requêtes `complete` concurrentes.** Un seul admin est créé, la seconde requête reçoit 410 Gone, et le jeton est invalide après usage. Test : Task 11.
