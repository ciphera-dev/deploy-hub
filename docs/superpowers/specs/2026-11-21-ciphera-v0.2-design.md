# Ciphera v0.2 — « plusieurs serveurs, données et équipe » — design

- Date : 2026-11-21
- Statut : approuvé (2026-11-21)
- Prérequis : v0.1 livrée (`2026-11-21-ciphera-v0.1-design.md`). Les décisions de son §7 restent valables : proxy et agent par nœud, réseau Docker `ciphera`, sous-processus `docker compose` / `railpack` à arguments fixes, Postgres et BuildKit en conteneurs épinglés, updater oneshot, table `environments`, cinq rôles, métriques de base collectées.
- Entrées : `docs/design/screens.md`, `docs/architecture/stack.md`, `docs/adr/0002-terminal-et-actions-serveur.md`, `docs/security/exigences.md`, `docs/research/analyse-paas/` (phase 1 « parité cœur » et une partie de la phase 2).

## 1. Intention et pourquoi

La v0.1 prouve qu'on déploie une app sur un serveur. La v0.2 rattrape **la parité cœur** de Dokploy et Coolify, celle que les utilisateurs comparent : plusieurs serveurs, bases de données managées avec sauvegardes, monitoring, travail en équipe avec rôles et audit, terminal.

L'avantage de Ciphera se joue ici :
- **multi-serveur sans SSH ni socket Docker exposé**, grâce à un agent QUIC + mTLS ;
- **RBAC et audit inclus gratuitement**, ce que Dokploy réserve à sa licence DSAL.

## 2. Objectifs, non-objectifs, anti-objectifs

**Objectifs v0.2 :**
1. **Multi-serveur :**
   - écran « Ajouter un serveur » (`Servers.jsx#AddServerModal`) : commande `curl … | sh -s -- --join <jeton>` ou conteneur, jeton join à usage unique valable 15 min et stocké en hash, attente de l'agent par SSE, états « délai dépassé » et « échec » ;
   - l'agent distant s'enrôle, la mini-PKI émet son certificat mTLS (rotation automatique, révocation à la suppression) ;
   - liste des serveurs avec globe et onglet Clés SSH (`ServersPage.jsx`) ;
   - gestion d'un serveur (`ServerManage.jsx`) : redémarrage, mise à jour système, mise à jour de l'agent, renouvellement de certificat, drainage, reset root (re-auth + MFA).
2. **Placement :** chaque environnement d'un projet choisit son serveur. Les déploiements sont envoyés à l'agent de ce serveur, et le proxy de ce nœud sert les domaines.
3. **Bases de données managées** (`Databases.jsx`) :
   - PostgreSQL, MySQL, MariaDB, MongoDB, Redis ;
   - création, version, stockage, connexions ;
   - identifiants révélés seulement après re-auth, avec audit ;
   - rotation du mot de passe ;
   - réplicas en lecture pour PostgreSQL seulement ;
   - injection automatique de `DATABASE_URL` dans les variables du projet lié.
4. **Sauvegardes** (`Backups.jsx`) :
   - destinations S3-compatibles et Supabase Storage ;
   - planification et rétention (7 / 14 / 30 / 90 j) ;
   - sauvegarde des bases et des volumes, restauration (re-auth) ;
   - snapshots de serveur limités aux volumes Ciphera.

   Les identifiants S3 sont chiffrés avec age, en écriture seule, et jamais stockés côté navigateur.
5. **Monitoring** (`Pages2.jsx#MonitoringV2`, fusionné avec les blocs utiles de `Monitoring.jsx` : multi-séries, conteneurs gourmands, répartition du stockage) :
   - métriques par serveur et par conteneur ;
   - **alertes et seuils** avec notification ;
   - export Prometheus et OTLP ;
   - lien Grafana optionnel.
6. **Équipe** (`Team.jsx`) :
   - membres, invitations, mot de passe temporaire avec changement forcé, suspension, reset MFA ;
   - **matrice de permissions éditable** (owner) ;
   - **périmètre par projet** ;
   - **journal d'audit** (onglet Équipe, plus une page globale « Audit », écran manquant) ;
   - 2FA obligatoire par organisation ;
   - **SSO SAML/OIDC inclus**.
7. **Terminal** (`Terminal.jsx`, selon l'ADR 0002) :
   - xterm.js et WebSocket via l'agent, avec le message `TerminalOpen` distinct dans `proto` ;
   - désactivé par défaut, owner/admin, re-auth + MFA ;
   - session enregistrée dans l'audit, expiration après inactivité ;
   - refusable par l'agent (`terminal = false`) ;
   - exec dans un conteneur via bollard.
8. **Conteneurs** (`Docker.jsx`) : stacks Compose, images, volumes, start/stop/restart/inspect, prune. Logs par conteneur. Shell = terminal, avec les mêmes règles.
9. **DNS Cloudflare :**
   - **connecteur Cloudflare** (`ProjectCloudflare.jsx`, carte Cloudflare des Connecteurs) en OAuth ou par token restreint aux zones choisies ;
   - **DNS-01** pour les certificats wildcard ;
   - page **Domaines globale** (`DomainsPage.jsx`) avec zones, enregistrements et actions groupées.
10. **Notifications** : canaux Slack, Discord, Telegram, e-mail et webhook simple ; matrice événements × canaux dans le profil (`ProfileNotif.jsx`) ; mode « Ne pas déranger ».
11. **Environnements multiples :** création de `staging` et d'environnements libres (branche, serveur, domaines et variables propres). Le sélecteur porté en v0.1 devient complet.
12. **Clés API** (`ApiPage.jsx`) :
    - jetons `cph_*` à permissions, avec expiration et liste d'IP autorisées, affichés une seule fois ;
    - **CLI `ciphera-cli`** publiée (clap + client progenitor), installable par le même canal signé.
13. **Sources Git hors GitHub** (reportées de la v0.1, décision utilisateur 2026-11-23) : URL Git publique ou clé de déploiement ; GitLab, Gitea et Bitbucket via URL + webhook générique signé (HMAC). Les tuiles de `Projects.jsx#NewProjectModal`, désactivées en v0.1, sont activées.

**Non-objectifs v0.2 (en v0.3) :**
- CrowdSec, pare-feu et scan malware ;
- connecteurs IA ;
- webhooks sortants ;
- tickets ;
- previews de PR ;
- catalogue de templates ;
- Tailscale ;
- espaces de travail multiples ;
- documentation intégrée ;
- MCP.

Hors périmètre : HA du plan de contrôle, clustering.

**Anti-objectifs :**
- L'agent distant accessible autrement qu'en QUIC + mTLS (pas de port Docker, pas de SSH requis par Ciphera).
- Une requête qui franchit le périmètre projet d'un membre : des tests d'autorisation croisés automatisés sont obligatoires (403 attendus).
- Un identifiant de base ou de S3 affiché sans re-auth, ou écrit dans un log.
- Un terminal ouvert sans audit, ou actif par défaut.
- SSO ou audit payants.

## 3. Contraintes

- Le protocole `proto` monte en **v2 avec compatibilité v1**. Le plan de contrôle accepte des agents v1 et v2 pendant une version.
- Les migrations SQL sont additives seulement depuis la v0.1, sans perte de données.
- Les images des bases sont épinglées par digest. Les mots de passe sont générés par `OsRng`.
- Le reste suit les contraintes de la v0.1 (§3).

## 4. Approches envisagées

| Approche | Principe | Pour | Contre |
|---|---|---|---|
| **A. Tranches verticales** (retenue, cohérente avec la v0.1) | Une fonction à la fois de bout en bout, en commençant par le multi-serveur | Chaque tranche est visible et testée ; le multi-serveur valide tôt le protocole v2 | Le monitoring et l'équipe arrivent après les données |
| B. Équipe et RBAC d'abord | Rôles éditables, audit et SSO avant tout le reste | Le modèle d'autorisation est figé tôt | Le multi-serveur, attendu le plus, arrive tard |

**Retenue : A** (choix de l'utilisateur pour la méthode, reconduit). Ordre proposé par le rédacteur : multi-serveur d'abord, car tout le reste s'appuie sur le placement.

## 5. Forme de la v0.2 (tranches)

1. **Protocole v2 + enrôlement distant + serveurs :** liste, ajout, gestion, clés SSH (générées en WebCrypto côté navigateur, clé privée jamais transmise).
2. **Placement des environnements + environnements multiples.**
3. **Bases de données managées.**
4. **Sauvegardes et restauration.**
5. **Monitoring + alertes + notifications multicanal.**
6. **Équipe :** matrice éditable, périmètre projet, audit global, SSO, mot de passe temporaire.
7. **Conteneurs + terminal** (ADR 0002), avec revue de sécurité dédiée avant fusion.
8. **Cloudflare :** connecteur, DNS-01, page Domaines globale.
9. **Clés API + CLI publiée.**
10. **Durcissement :**
    - tests d'autorisation croisés ;
    - fuzzing des messages `proto` ;
    - tests de rotation et révocation des certificats ;
    - mise à jour du threat model ;
    - `security-audit` sur les nouvelles surfaces (agent distant, terminal, sauvegardes).

## 6. Laissé au constructeur

- Le moteur de sauvegarde : SDK S3 natif Rust ou rclone en sous-processus à arguments fixes, à noter en décision.
- Le format de stockage des métriques au-delà de la v0.1 : partitionnement Postgres ou TimescaleDB optionnel. Pas de base supplémentaire obligatoire.
- La bibliothèque SAML/OIDC.
- Le format d'enregistrement des sessions terminal (asciicast v2 recommandé).
- Le détail des unités et seuils d'alerte par défaut.
