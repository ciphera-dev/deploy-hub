## 1. Intention et pourquoi

Ciphera est un PaaS auto-hébergé, **100 % open source (AGPL-3.0)**, qui fait aussi bien que Dokploy et Coolify en plus léger (un binaire, pas de Redis, agent natif) et plus sûr. La sécurité se construit dès le jour 1 : pas d'exécution shell interpolée, mTLS, secrets en écriture seule, releases signées. Les deux concurrents ont accumulé des CVE critiques en 2025-2026 (`03-securite-et-cve.md`).

La **v0.1** prouve la promesse de base sur **un seul serveur** : un utilisateur installe Ciphera en une commande, se connecte avec une 2FA, branche un dépôt Git et obtient son app en ligne en HTTPS, avec logs, variables secrètes et rollback.

## 2. Objectifs, non-objectifs, anti-objectifs

**Objectifs v0.1 :**
1. **Installation et premier accès :**
   - `curl -fsSL https://get.ciphera.ch/install.sh | sh` installe les binaires vérifiés (minisign + SHA-256), les unités systemd, PostgreSQL et BuildKit sur une machine Linux (Debian, Ubuntu, Fedora ; amd64/arm64).
   - L'assistant web crée le premier admin avec un jeton de setup à usage unique.
2. **Authentification :**
   - e-mail + mot de passe (argon2id) ;
   - TOTP **et** passkeys (WebAuthn) ;
   - codes de secours ;
   - sessions révocables.

   L'inscription se fait sur **invitation seulement** : l'inscription ouverte existe en option, désactivée par défaut.
3. **Un serveur :** l'agent tourne sur la même machine que le plan de contrôle. Il passe **quand même** par QUIC + mTLS et le protocole `crates/proto`, comme s'il était distant, pour que le multi-serveur de la v0.2 ne demande aucune réécriture.
4. **Projets :**
   - création depuis un dépôt GitHub (GitHub App de l'instance ou dépôt public) ou depuis une image Docker ;
   - *(décision utilisateur 2026-11-23 : URL Git publique ou clé de déploiement, et GitLab, Gitea et Bitbucket via URL + webhook générique, passent en v0.2 ; voir les non-objectifs)* ;
   - builds **Railpack** (par défaut), **Dockerfile**, **Compose** via BuildKit.
5. **Déploiements :**
   - déclenchés par push (webhook signé HMAC), manuellement ou par deploy hook ;
   - pipeline visible : clone, build, image, start, healthcheck, switch ;
   - **zéro interruption** (le nouveau conteneur doit être sain avant le basculement) ;
   - **rollback en un clic** : les N dernières images sont conservées (N = 5 par défaut).
6. **Logs en direct** : build et runtime par conteneur, par WebSocket.
7. **Variables d'environnement :** par projet et par environnement, avec secrets chiffrés (age) en écriture seule, mode `.env` et bannière « non appliquées ». Les variables globales sont dans la v0.1, car l'écran les hérite.
8. **Domaines :**
   - domaine personnalisé et domaine généré ;
   - HTTPS automatique via Pingora + instant-acme (HTTP-01 ; DNS-01 Cloudflare en v0.2) ;
   - redirection 308, domaine principal, vérification DNS.
9. **Vue d'ensemble et Déploiements (global)**, branchés sur les vraies données du serveur unique.
10. **Paramètres** limités à : Général, Domaine du panel (HTTPS, sans Tailscale en v0.1), Déploiements (rétention), Notifications (SMTP), Sécurité de l'organisation (2FA obligatoire, liste d'IP autorisées), Zone de danger.
11. **Profil** : informations, sécurité (mot de passe, TOTP, passkeys, sessions), notifications e-mail minimales si SMTP est configuré (déploiement réussi, échec de build ou de déploiement, certificat en échec ou proche de l'expiration).
12. **Mises à jour de Ciphera** depuis la même source signée, avec verrou anti-parallélisme et sauvegarde de la base avant mise à jour.

**Non-objectifs v0.1 (repoussés, écrans conservés en maquette) :**
- **v0.2 :**
  - multi-serveur (ajout de serveur, jetons join) ;
  - bases de données managées ;
  - sauvegardes S3 ;
  - monitoring et métriques ;
  - équipe et rôles (matrice complète, audit) ;
  - terminal (ADR 0002) ;
  - conteneurs (page Docker) ;
  - DNS Cloudflare ;
  - notifications Slack/Discord ;
  - sources Git hors GitHub : URL Git publique ou clé de déploiement ; GitLab, Gitea et Bitbucket via URL + webhook générique (décision utilisateur 2026-11-23 ; tuiles visibles et désactivées avec un badge v0.2 dans « Nouveau projet »).
- **v0.3 :**
  - sécurité (CrowdSec, pare-feu, malware) ;
  - connecteurs IA ;
  - webhooks sortants ;
  - tickets et ticket IA ;
  - previews de PR ;
  - catalogue de templates ;
  - Tailscale ;
  - espaces de travail multiples ;
  - documentation intégrée.
- Paquets .deb/.rpm, HA du plan de contrôle, clustering.

**Anti-objectifs (échec même si « ça marche ») :**
- Toute exécution shell construite à partir d'une entrée utilisateur (CWE-78), dans l'agent ou ailleurs.
- Un secret renvoyé par l'API, écrit dans un log ou stocké côté navigateur.
- Une ressource tierce chargée par le panneau (CDN, polices, favicons) : le panneau doit fonctionner hors ligne.
- Une fonctionnalité réservée à une licence, ou une télémétrie active par défaut.
- Un écran redessiné au lieu d'être porté, alors que la maquette existe.
- Un mot de passe de base généré de façon prévisible ou codé en dur (leçon CVE-2026-24840 de Dokploy).

## 3. Contraintes

- **Stack imposée** (stack.md) : React 19 + Vite + TS + TanStack Router/Query + Tailwind v4 + shadcn/ui, embarqué via rust-embed. Axum + PostgreSQL 17 + SQLx, files de tâches en Postgres. webauthn-rs + TOTP. age. OpenTelemetry/Prometheus. Agent Tokio + quinn + rcgen + bollard + rusqlite. BuildKit + Railpack. Pingora + instant-acme. CLI clap.
- **Plateformes serveur** : Linux x86_64 et aarch64, binaires musl statiques. Docker Engine requis sur le nœud (installé par `install.sh` s'il manque, avec l'accord de l'opérateur, en mode interactif). Développement possible sous Windows : lancer cargo depuis PowerShell, les builds et tests d'intégration tournent dans Podman/WSL.
- **Sécurité** : `docs/security/exigences.md` s'applique à chaque tâche. Pas de tâche backend avec un ❌ ouvert dans `fondations.md` (0 aujourd'hui).
- **Mémoire** : chaque tâche terminée est écrite dans `.agents/memory/` (journal + `etat.md`).
- **Aucune trace d'IA** dans les fichiers ; `npx design-to-dev ai-traces scan . --strict` avant chaque commit.

## 4. Approches envisagées

| Approche | Principe | Pour | Contre |
|---|---|---|---|
| **A. Tranches verticales** (retenue) | Squelette qui traverse tout (install → binaire + SPA → login → agent local), puis une fonction à la fois de bout en bout (écran porté + endpoint + agent + test) | Les parties risquées (agent mTLS, BuildKit, ACME) sont testées en continu ; chaque étape est visible dans le vrai panneau | Les écrans sont portés au fil de l'eau |
| B. Backend d'abord | Crates jusqu'au déploiement en CLI, puis interface | Fondations solides | Rien de visible longtemps ; contrat API à retoucher au branchement |
| C. Interface d'abord | ~20 écrans sur MSW, puis backend | Panneau visible vite | Panneau « faux » longtemps ; sécurité et agent tardifs |

**Choix de l'utilisateur : A.**

## 5. Décisions prises (à respecter telles quelles)

- **Ordre de livraison** : v0.1 → v0.2 → v0.3, contenu en §2.
- **Inscription** : invitation seulement par défaut, le premier admin passe par l'assistant d'installation.
- **Terminal** : en v0.2, selon l'ADR 0002 (désactivé par défaut, owner/admin, re-auth + MFA, audité).
- **Licence** : AGPL-3.0-only, à reporter dans `Cargo.toml` et `web/package.json`.
- **Open source intégral** : pas de licence, pas de facturation, SSO inclus (v0.2+).
- **Écrans** : chaque écran v0.1 est porté depuis `prototypes/dashboard/` (contrat dans `docs/design/screens.md`), jamais redessiné. Les manquants nécessaires en v0.1 sont dessinés avec les composants et tokens existants :
  - nouveau mot de passe ;
  - acceptation d'invitation ;
  - enrôlement TOTP / passkey + codes de secours ;
  - erreurs 500 / API injoignable / session expirée ;
  - 403 ;
  - skeletons ;
  - modale « jeton créé » ;
  - détail de déploiement par URL.
- **Avatars** : initiales + upload, pas de galerie.

## 6. Forme de la v0.1 (tranches, dans l'ordre)

0. **Socle du dépôt :**
   - `git init` ;
   - workspace Cargo (`crates/*` vides qui compilent) ;
   - `rust-toolchain.toml`, `deny.toml`, `justfile` ;
   - `web/` initialisé dans le dossier existant (Vite react-ts, Tailwind v4, shadcn, TanStack, Vitest, MSW, Playwright) ;
   - CI (fmt, clippy, test, `cargo audit/deny`, `npm audit`, shellcheck, actionlint, ai-traces) ;
   - tokens → `@theme`, composants `core/` en TSX avec tests.
1. **Squelette qui traverse tout :**
   - `control-plane` sert la SPA embarquée et `GET /api/health` **en HTTPS auto-signé** (empreinte affichée par `install.sh`) ;
   - migrations SQLx initiales ;
   - shell porté (sidebar, header, routes vides) ;
   - `install.sh` (vérification minisign + SHA-256, systemd) testé en conteneur ;
   - release CI signée ;
   - assistant d'installation porté et branché ;
   - jeton de setup.
2. **Authentification :** login, 2FA (TOTP + WebAuthn + codes), sessions, invitation, nouveau mot de passe, profil › sécurité.
3. **Agent local :**
   - mini-PKI ;
   - enrôlement local automatique à l'installation ;
   - QUIC + mTLS ;
   - protocole `proto` v1 (deploy/stop/logs/metrics/pull) ;
   - bollard ;
   - état SQLite.
4. **Projets + build** : GitHub App par instance (carte GitHub des Connecteurs), création (Git/image), Railpack/Dockerfile/Compose via BuildKit, liste des projets, détail projet › aperçu/services.
5. **Déploiements** : file Postgres, pipeline, zéro interruption, rollback, webhooks Git HMAC, deploy hooks, logs live, page Déploiements globale, détail par URL.
6. **Variables** (projet + globales, age, écriture seule).
7. **Proxy + domaines** : Pingora + instant-acme, domaines du projet, domaine du panel, HTTPS du panel.
8. **Vue d'ensemble, Paramètres (sections v0.1), notifications de base, mises à jour de Ciphera.**
9. **Durcissement :**
   - CSP et en-têtes ;
   - rate limiting ;
   - tests d'autorisation (403 attendus) ;
   - threat model publié ;
   - tests de bout en bout d'installation (refus si checksum ou signature invalide) ;
   - revue de sécurité (`security-audit`).

Chaque tranche se termine par :
- les tests verts ;
- l'écran porté visible dans le binaire ;
- la ligne de `docs/design/screens.md` passée à `branché` ;
- la mémoire à jour.

## 7. Décisions issues de la relecture (2026-11-21)

### Décidées par l'utilisateur

1. **Premier accès : certificat auto-signé + empreinte.**
   - `install.sh` génère un certificat auto-signé (rcgen, via `ciphera init`) et affiche l'URL `https://<IP>:<port>/setup?token=…` avec l'**empreinte SHA-256** du certificat.
   - Le panneau n'écoute jamais en HTTP clair, hormis une redirection 80 → 443 sans contenu.
   - L'assistant propose ensuite de passer sur un domaine (ACME HTTP-01 via le proxy).
   - Conséquence : **le TLS du panneau (auto-signé) arrive dès la tranche 1**. L'ACME du panneau reste en tranche 7.
2. **GitHub : GitHub App par instance (flux « manifest », comme Coolify).**
   - Créée depuis le panneau, avec des permissions fines par dépôt, des webhooks automatiques et des jetons d'installation de courte durée.
   - La clé privée de l'App et le secret de webhook sont chiffrés avec age, en écriture seule.
   - La **carte GitHub de la page Connecteurs** est portée en v0.1, seulement elle. Elle est nécessaire à la tranche 4. Les autres fournisseurs passeront par URL Git + clé de déploiement + webhook générique, en v0.2 (décision utilisateur 2026-11-23).
3. **Infrastructure de release : rien n'existe encore.**
   - Le plan prévoit une **chaîne de release de test** : clé minisign de test, serveur HTTP local qui sert les artefacts, `install.sh` paramétrable par `CIPHERA_RELEASE_BASE_URL` en test uniquement.
   - Une tâche dédiée, avant la première release publique, couvre : créer le dépôt GitHub public, le domaine `get.ciphera.ch` (GitHub Releases + redirection), la vraie clé minisign hors dépôt, l'environnement CI protégé et cosign keyless.

### Choix du rédacteur (à relire)

4. **Proxy et réseau :**
   - Un `ciphera-proxy` **par nœud**, piloté par **l'agent local** via `proto`. Le plan de contrôle envoie à l'agent les routes désirées : domaine → service → conteneurs sains. L'agent les applique au proxy par une socket Unix locale.
   - Les conteneurs sont sur un réseau Docker dédié `ciphera` et sont joints par leur IP de réseau, sans port publié sur l'hôte.
   - Zéro interruption : le nouveau conteneur démarre, passe son healthcheck, l'agent bascule l'upstream dans le proxy, puis vide l'ancien.
   - Le rollback rebascule sur une image conservée.
   - Ce modèle sert tel quel au multi-serveur de la v0.2 : un proxy et un agent par nœud.
5. **Compose et Railpack sans shell :**
   - Le binaire `docker compose` (plugin officiel) et le binaire `railpack` sont appelés **en sous-processus avec un tableau d'arguments fixe**, jamais via un shell ni par interpolation. Les chemins et noms de projet sont validés par une liste blanche (regex) avant l'appel.
   - Ce ne sont pas des « commandes arbitraires » : binaire fixe, sous-commandes fixes, entrées validées. Cela respecte l'anti-objectif CWE-78.
   - Railpack produit le plan de build, et BuildKit le construit.
   - Pour un projet Compose :
     - le domaine est rattaché à un service choisi ;
     - « image conservée » veut dire l'ensemble des images du projet à un déploiement donné ;
     - le rollback redéploie cet ensemble ;
     - le zéro interruption s'applique au service exposé, les autres sont redémarrés dans l'ordre de `depends_on`.
6. **PostgreSQL et BuildKit :**
   - PostgreSQL 17 et `buildkitd` tournent comme **conteneurs gérés par Ciphera**, avec des images épinglées par digest SHA-256 et des données dans des volumes nommés. Cela fonctionne pareil sur Debian, Ubuntu et Fedora, en amd64 comme en arm64.
   - Le mot de passe de la base est généré par `ciphera init` (`OsRng`, 32 octets) et stocké en fichier 600, jamais affiché.
   - La sauvegarde avant mise à jour se fait par `pg_dump` dans le conteneur.
7. **Utilisateurs système et mises à jour :**
   - `ciphera` (plan de contrôle) et `ciphera-proxy` tournent sous des utilisateurs dédiés non privilégiés, avec durcissement systemd (`NoNewPrivileges`, `ProtectSystem=strict`…). Le proxy reçoit `CAP_NET_BIND_SERVICE`.
   - `ciphera-agent` est membre du groupe `docker`, ce qui équivaut à root et est documenté dans le threat model.
   - Les mises à jour passent par une unité oneshot `ciphera-updater.service`, déclenchée par une unité `.path` quand le plan de contrôle dépose une demande signée. L'updater vérifie minisign et SHA-256, pose un verrou (`flock`), fait le `pg_dump`, remplace les binaires, redémarre les services, et revient en arrière si le healthcheck échoue.
8. **Environnements :**
   - Le schéma SQL inclut **dès la v0.1** la table `environments` (projet → environnement → services → déploiements, domaines, variables).
   - L'interface v0.1 crée un seul environnement `production` par projet. Le sélecteur d'environnement de la maquette est porté, mais ne propose que celui-là. Preview et staging arrivent en v0.2/v0.3 sans migration cassante.
9. **Rôles :**
   - Les cinq rôles (owner, admin, ops, developer, viewer) existent dès la v0.1 avec la **matrice par défaut fixe** de `Team.jsx`. Une invitation choisit un rôle.
   - L'édition de la matrice, le périmètre par projet et l'écran Équipe complet arrivent en v0.2.
   - Les tests 403 de la tranche 9 couvrent la matrice fixe.
10. **SMTP :**
    - La section **Paramètres › Notifications** est portée en v0.1 avec la configuration SMTP.
    - Sans SMTP :
      - une invitation produit un **lien à usage unique à copier**, valable 72 h ;
      - « mot de passe oublié » affiche « contactez un administrateur » ;
      - un admin peut générer un lien de réinitialisation ;
      - `ciphera admin reset-password` (CLI, sur le serveur) sert de dernier recours.
11. **Vue d'ensemble :**
    - L'agent remonte dès la v0.1 les métriques de base de son nœud et des conteneurs (`proto metrics` : CPU, RAM, disque, réseau, toutes les 30 s).
    - Le plan de contrôle les agrège dans PostgreSQL : rétention de 30 jours, agrégats horaires au-delà de 24 h.
    - L'écran garde tous ses blocs. Le monitoring détaillé (alertes, seuils, page Monitoring) reste en v0.2.
